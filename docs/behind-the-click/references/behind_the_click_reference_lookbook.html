02 / THE SCROLL NARRATIVE

Make the invisible
understandable.

A continuous visual identity, not one camera flying endlessly through unrelated objects. Physical environment → logical explanation → genuine learning evidence.

Design target: a leisurely 90–120-second journey, entirely user-paced. Persistent course navigation, chapter links and a reduced-motion version must bypass the spectacle without losing content.

01
THE ARRIVAL

Production is where theory ends.

Human-height camera in a near-dark server aisle. Restrained forward movement towards one distant light. A small HTML line immediately explains the offer: hands-on Docker, Kubernetes, AWS, Terraform and CI/CD courses.

SCROLL / INTERACTION

The visitor controls progress with normal scroll. No intro timer, sound gate, mandatory loader, or hidden course navigation.

WHY THIS SCENE EXISTS

Emotion: this is serious engineering. Clarity: this is a course website.

Suggested destination Explore courses · See the journey
02
THE MISSION

The code is ready. The system isn’t.

A precise match-cut to an engineering console in the same visual world. One fictional ticket-booking application works locally. Its service name, tickets-api, remains visible through the rest of the story. Opening night is approaching.

SCROLL / INTERACTION

State the task plainly: get this application ready for launch. Keep the app preview as a persistent small anchor during later chapters.

WHY THIS SCENE EXISTS

The story is no longer an unexplained trip through servers. There is a person, an application, and a job to do.

Suggested destination Mission: prepare the app for opening night
03
DOCKER / PACKAGE

Ship the environment. Not just the code.

A labelled diagnostic view reveals application code, dependencies and runtime requirements. These assemble into a versioned image. Development and staging reference that same artifact.

SCROLL / INTERACTION

One scroll beat exposes the ingredients; the next packages them. Avoid whales, shipping containers and a cloud of glowing logos.

WHY THIS SCENE EXISTS

Learning payoff: package and run an application consistently, while understanding the remaining environment and configuration differences.

Suggested destination Preview the Docker lesson
04
AWS + TERRAFORM / PROVISION

Give it a home. Make that home reproducible.

First reveal a logical cloud environment: access, networking and compute. Then show Terraform configuration, a reviewed plan, and an applied change reflected in the environment. These are two separate beats.

SCROLL / INTERACTION

Clearly label this view PROVISION. It is not a journey taken by each user request and does not imply one application request runs Terraform.

WHY THIS SCENE EXISTS

AWS explains the cloud resources. Terraform explains how their desired configuration is managed through code.

Suggested destination Explore AWS · Explore Terraform
05
KUBERNETES / RUN

One application. Ready for more.

Transition into a logical workload view. Increasing simulated demand leads a configured autoscaler to request more replicas. A new replica progresses through starting and ready states before receiving traffic.

SCROLL / INTERACTION

Keep the animation legible and restrained. Show finite capacity; avoid instant, unlimited, magical scaling. Explain replica as another running copy of the application.

WHY THIS SCENE EXISTS

Learning payoff: deploy, scale and troubleshoot containerised workloads. The lab teaches why configuration, readiness and capacity matter.

Suggested destination Explore Kubernetes
06
CI/CD / RELEASE

Improve the app. Without gambling on the release.

A new application version passes through a clear build-and-test workflow. An intentionally failing test blocks one attempt. A corrected version passes the configured checks and moves through a controlled deployment.

SCROLL / INTERACTION

Label this view RELEASE. Keep the running app visible beside the delivery workflow so the purpose stays obvious.

WHY THIS SCENE EXISTS

Learning payoff: automate checks and delivery. Do not portray every pipeline as automatically rolling back or guaranteeing zero downtime.

Suggested destination Explore CI/CD
07
THE PROOF / OPTIONAL INTERACTION

Now test it.

Invite the visitor to stop one replica in a labelled simulation. Other ready replicas continue serving in this configured scenario; a replacement starts and becomes ready. The booking confirmation stays visible.

SCROLL / INTERACTION

Use a real HTML button: Stop one replica. A small diagnostic panel explains the event and recovery. The same result is available without animation or a mouse.

WHY THIS SCENE EXISTS

Final line: To the user, nothing happened. That’s the point. This is a demonstration of one prepared failure scenario—not a universal availability promise.

Suggested destination Understand the recovery · Preview a real lab
08
THE OFFER / LEARN

You’ve seen what it does. Now learn how to build it.

The system view becomes a normal, readable curriculum map. Docker packaging, cloud infrastructure, Terraform configuration, Kubernetes workloads and CI/CD each point to the relevant course.

SCROLL / INTERACTION

Offer one connected learning path plus individual courses. Ask where the learner is starting, not which floating logo looks most interesting.

WHY THIS SCENE EXISTS

Replace demonstration with evidence: an actual sample lesson, real lab interface, instructor, syllabus, prerequisites, time commitment, transparent pricing and support terms.

Suggested destination Choose my starting point · View the complete path
03 / THE PURCHASE DECISION

Sell the capability.
Prove the teaching.

The simulation earns attention. Real learning evidence must earn the purchase. No invented testimonials, salary promises, completion rates or countdowns.

I want this capability.

The story makes packaging, provisioning, scaling, releasing and recovery visible. Each capability points directly to an accurately named course.

I believe you can teach it.

Show an actual instructor, sample lesson, lab interface, project outputs and how students get feedback. Distinguish simulation from hands-on lab work.

I know where to start.

Offer an on-ramp, a connected path and individual courses. State prerequisites, total price, expected effort, access duration and support clearly.

04 / IMPLEMENTATION DIRECTION

Build the first
credible minute.

Approve the story in still frames before building a complex animation system. Prototype the Arrival and mission first, then connect the teaching and purchase flow.

Prototype and production

Storyboard the layout in Figma. Author believable assets in Blender; Spline is an option for an early scene prototype. For the full interactive system, evaluate one shared Three.js / React Three Fiber canvas with native-scroll-driven GSAP animation and ordinary HTML content.

Real-time rendering is not mandatory everywhere. A pre-rendered introduction plus an interactive climax may be appropriate, but compare loading, seeking, memory and device performance before choosing.

Performance and access

Load the course offer before the heavy scene. Compress and reuse assets, limit live lights and post-processing, stop rendering when idle, and provide an illustrated fallback. Mobile gets the same story with simpler framing—not a squeezed desktop camera path.

Target LCP ≤ 2.5 s, INP ≤ 200 ms and CLS ≤ 0.1 at the 75th percentile, separately for desktop and mobile. Also profile frame pacing and memory. Keep all purchasing and learning information outside the canvas.

Technical truth in the visual language

Separate BUILD, PROVISION, RELEASE and RUN views. Do not animate Docker, Terraform and a delivery pipeline as sequential network hops for a booking request. Label software topology as logical rather than pretending a Pod is a physical server.

Scaling and recovery scenes need explicit configuration, capacity and readiness assumptions. The demonstration is a controlled example, not a promise of unlimited capacity or universal zero downtime.

Validation before expansion

Ask target learners what is sold, what the application needs, what each course changes and where they would begin. If they cannot explain the story, revise it before adding visual complexity.

Compare the cinematic page with a clear static page using the same course offer. Measure enrolment and qualified trial engagement, not scroll depth alone. Watch mobile exits, technical failures and accessibility regressions.
